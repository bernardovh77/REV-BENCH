# Stage 124 — The application's foundation

Specification: [docs/roadmap/07-app.md](roadmap/07-app.md#stage-124); design:
[docs/app-design.md](app-design.md) sections 2–5, 9–13 and 15.

**Status: done on Windows, with three things CI and Bernardo's machine still have to confirm**
(listed under "Not verified"). The Electron application plays the real engine through the real
Node-API add-on on the null audio backend, is tested end to end, and builds an unsigned Windows
installer and a portable zip whose unpacked app and extracted zip were started here.

The stage ran in two parts by two builders against two fixed contracts
([`app/src/shared/addon.ts`](../app/src/shared/addon.ts), the add-on's API, and
[`app/src/shared/protocol.ts`](../app/src/shared/protocol.ts), the window and the engine
process): builder A made the add-on (`app/native/`, detailed in
[docs/stage-124-addon.md](stage-124-addon.md), kept as this record's annex), builder B the rest of
`app/`, first against a fake add-on (phase 1) and then on the real one with the end-to-end test,
the measurements and the packages (phase 2). Neither contract was changed.

### Where the add-on lives (one convention)

The add-on build always writes `<build folder>/rb_native.node` (A's CMake).
- **Development:** `app/native/build/rb_native.node`, made by `python tools/build_addon.py`
  (`npm run build:native` calls it). Git-ignored by the root `.gitignore`'s `build/`.
- **Tests:** `<out>/addon-build/rb_native.node`, made by `tools/run_tests.py addon` and, again if
  needed, by `app-e2e`; the suites hand it to the app as `RB_NATIVE_PATH`.
- **A package:** `<resources>/rb_native.node`, beside the asar (see 6).

The engine process looks in `$RB_NATIVE_PATH`, then `<resources>/rb_native.node`, then the
development place (`src/engine/addon-loader.ts`), and **never falls back to the fake**: a missing
add-on is a `fatal` message and the window says why (e2e-tested).

**cmake-js and node-api-headers are pinned in one place, `app/native/build-tools/`** (their own
package.json and lock, with A's `semver` override), installed outside the repo by the
`addon`/`app-e2e` suites and `build_addon.py`/`package_app.py` (all through
`run_tests.addon_build_commands`). They are not in `app/package.json` (phase 1 had put them
there; one place is enough and the `addon` suite works from it). `tools/test_package_app.py`
checks that nothing pins them twice.

## 2. The processes and the channel (as built)

- **Main process** (`dist/main/main.cjs`): window, menu stub, the supervisor, logs and the autosave
  in the user-data folder, `platform.ts` for everything system-specific. It never touches the
  sound or the telemetry.
- **Engine process** (`dist/engine/engine.cjs`, an Electron `utilityProcess`): loads the add-on,
  makes the host (null backend when `RB_BACKEND=null`, else the system's default device), runs the
  control loop: commands → host calls → replies with the window's own id; a rebuild is prepare,
  polled wait, swap; snapshot and statistics requests. **The app builds every engine with a free
  crank (`hold` 0)**: the core's default is a crank held by a dyno at 0 rpm, for offline renders,
  and with it the real engine never turned (found by the first real end-to-end run). It goes in the
  build itself (`BuildSpec.params`), for the first engine and every swap.
- **Window** (sandboxed Svelte 5): a store that asks for a snapshot every animation frame.
- **MessagePort:** a fresh `MessageChannelMain` per request and per engine restart; one end to the
  engine, the other to the window through the preload (`window.postMessage` with the port); the
  window asks (`requestEnginePort`), so there is no race with the page's load.
- **Crash handling:** the supervisor restarts a dead engine after 0.2, 0.5, 1, 2, then 4 s with the
  build the engine last said it made (autosaved atomically in `userData/session/build.json`); more
  than 5 deaths in 60 s is "failed" with a button; a saved build that keeps the engine from
  starting is dropped for the default build after two starts. The window is told every step. Logs:
  `userData/logs/rev-bench.log` (1 MB, then `.1`), including the engine's stdout and stderr.

Environment (tests and developers): `RB_FAKE_ADDON=1` (the test double: never chosen by itself),
`RB_BACKEND=null`, `RB_SAMPLE_RATE`, `RB_DEVICE`, `RB_USER_DATA`, `RB_NATIVE_PATH`.

## 3. The real add-on in Node and in Electron

- **Contract, in Node:** `tests/addon-contract.ts` is the add-on contract as a reusable test.
  `tests/addon-real.test.ts` runs it against `rb_native.node` (19 tests, the null backend; skipped
  unless `RB_NATIVE_PATH` names a built add-on, and a failure if `RB_REQUIRE_NATIVE=1`, as the
  `app-e2e` suite sets). It passes.
- **Electron 45's utility process loads the same `.node`** (A could only check Node): the engine
  process reaches "running", plays, and swaps engines under Playwright's Electron driver and from
  the packaged app (whose Electron is the real one, `RunAsNode` fuse off). Nothing had to change in
  the add-on.
- **Where the real add-on differs from the fake (and the contract test now says what the real one
  does; the fake follows it):**
  - `setParam` with an id the core doesn't have, or a value that isn't a number, doesn't throw: the
    command is acknowledged `refused` (codes -2 and -3); an id outside 0..65535 throws. The control
    loop checks names and finite values itself, so the window gets an error reply at once.
  - `readSnapshot()`'s info has the *host's* generation and sequence, not the bytes' (the core
    counts every engine build since its sim was made and every snapshot it took: the first engine's
    bytes said generation 2 where the host's said 1, and sequence 4 where the host's said 3). The
    protocol's `generation` and `sequence` are the host's; the decoded bytes carry the core's. The
    interface uses only the decoded snapshot, so the window shows the core's counts; anything that
    sends `expectedGeneration` must use `Host.generation()`.
  - `selectDevice` needs a started host (`RB_HOST_ERR_STATE` before `start()`), and an index that
    doesn't exist is `RB_HOST_ERR_DEVICE`.
  - Not found wanting: `prepare` of an unknown preset throws at once (`RB_ERR_ID`); `destroy()` marks
    first and frees; `stats()` has the render thread's priority (`MMCSS Pro Audio`, boosted) and 0
    forbidden calls.

## 4. End-to-end tests (`python tools/run_tests.py app-e2e`)

The suite builds the add-on, installs Electron's binary (`npx install-electron`: Electron 45's
`npm ci` doesn't download it), builds the app, runs the contract on the real add-on, then
`playwright test` (`e2e/`): the built app through Playwright's Electron driver, the real add-on, the
null backend (**never a sound device**), a fresh user-data folder each, one at a time.

| Test | What it checks |
| --- | --- |
| starts and plays | window "Engine running"; ignition and the starter bring the real engine to a speed of its own (> 500 rpm from real snapshots); the throttle raises it; no console errors |
| sandboxed in the real app | no `require`/`process` in the window; only the preload's five names; the policy meta; an inline script is refused |
| changes the engine | a swap to the V8; the select is enabled again; `build.json` has `v8-cross` |
| restarts after a kill | the engine process killed (its pid from the main process's status): "restarting", controls locked, then running again, `restarts` 1, a new pid, **the autosaved preset is back**, the new engine answers; the log has the death and the restart |
| quits cleanly | `app.close()`: the engine process is gone, the log has `engine stopped (exit 0)` and no error lines of ours |
| missing add-on | "Engine restarting" with `rb_native.node` in the message, the fatal line in the log, then "Engine stopped" and the restart button; no fallback to a fake |
| snapshot path (2 tests) | see 5 |

`python tools/run_tests.py addon app app-e2e` on this machine: addon 13 s, app 19 s (with
`npm ci`), app-e2e 71 s. The e2e tests drive a real window, so they need a desktop session
(Windows runners have one).

## 5. The snapshot path, measured

Engine process → `MessagePortMain` → the window's `MessagePort`, in the app as it runs (the real
add-on, the largest preset, the window asking once per animation frame), Windows 11, Electron 45,
2026-11-09 (`e2e/snapshot-path.spec.ts`; the numbers come from `<out>/app-e2e-results/*.json`).
Budget (contracts/runtime-v1.md): at most 64 KiB a snapshot, 60 a second, 3.75 MiB/s.
`MessagePortMain` can't transfer an `ArrayBuffer`, so each snapshot is **cloned once**.

| Measurement | Result |
| --- | --- |
| The V8's real snapshot | 624 bytes (a four: 464) |
| As the app uses it (a request every animation frame, here 120 a second) | 60.0 snapshots/s, **37.4 KB/s (1 % of the budget)** |
| The host's own rate | 60 a second: asking flat out gives the same 60/s, 37.3 KB/s |
| Time between two snapshots as the window sees them | median 16.6 ms, 95 % under 25 ms, longest 27 ms (the host's 60 Hz and the frame's phase) |
| Round trip of an always-answered request, 2000 samples | median 0.1 ms, 95 % 0.3 ms, 99 % 0.4 ms, longest 1.2 ms (timer resolution 0.1 ms); about 8,900 round trips a second |
| The engine process's CPU while this runs (the V8, low quality, real time) | about 10 % of a core |

The channel itself, with a stand-in utility process (`e2e/fixtures/blaster.cjs`) sending messages
of the sizes the budget allows to the window, 5 s each, `Date`-stamped on both sides:

| Message | Rate | Bytes/s | Delay median / 95 % / longest |
| --- | --- | --- | --- |
| 624 B | 60/s | 36.6 KB/s | 0.85 / 1.01 / 1.66 ms |
| 8 KiB | 60/s | 481 KB/s | 0.42 / 0.65 / 1.45 ms |
| **64 KiB (the budget's ceiling)** | 60/s | **3.77 MB/s (3.75 MiB/s)** | 1.31 / 1.89 / 2.74 ms |
| 64 KiB, as fast as it goes (3 s) | 6,100/s | 389 MB/s | 2.1 / 10.7 / 21 ms (a queue building up) |

So the clone costs about a millisecond at the budget's largest snapshot, six percent of a frame;
the budget is met with a wide margin, and stage 073's bigger snapshots have room to grow by more
than a hundred times before the channel is the limit. A frame is never late because of the
channel: the window draws the newest snapshot it has.

## 6. Packages (`python tools/package_app.py`)

`app/electron-builder.config.cjs` (electron-builder 26.18.0), unsigned, x64, built in a copy of
`app/` outside the repo with the add-on built first:
- **Files:** `dist/` only, in `app.asar` (268 KB): no source maps, no `node_modules`, **never the
  fake add-on**. The add-on goes in `resources/rb_native.node` (563 KB, no VC runtime DLL: only
  system DLLs), *beside* the asar through `extraResources`: a native library can't load from an
  archive, and that is where the engine process looks. The notices travel too:
  `THIRD_PARTY_NOTICES.md`, `licenses/Inter-OFL.txt`, `licenses/miniaudio-LICENSE.txt` (Electron's
  own `LICENSE.electron.txt` and `LICENSES.chromium.html` are in the folder).
- **Fuses**, checked in the built exe (`electron-fuses read`): `RunAsNode`, `NODE_OPTIONS` and
  `--inspect` off; `OnlyLoadAppFromAsar` and `EmbeddedAsarIntegrityValidation` on; cookie encryption
  on. `GrantFileProtocolExtraPrivileges` stays **on** because the window is loaded from a file; a
  custom protocol (a later stage) lets it go off. **Playwright's Electron driver needs the inspect
  flag, so the end-to-end tests drive the unpackaged app** (their fuses are Electron's defaults) and
  the packaged app is started by `e2e/packaged-smoke.mjs` with `--remote-debugging-port`, which no
  fuse governs, and driven over it.
- **Made here:** `Rev-Bench-Setup-0.1.0-x64.exe` (121.7 MB, NSIS, per user, choice of folder) and
  `Rev-Bench-0.1.0-win-x64.zip` (153.6 MB). The tool then checks the unpacked folder (add-on beside
  the asar, notices, nothing forbidden inside the asar, the fuses) and **starts the unpacked app and
  the app extracted from the zip** on the null backend: the window reaches "Engine running", the real
  engine runs on its own (770–790 rpm at idle), another engine can be chosen and is autosaved, quitting
  stops the engine process with exit 0, no error in the log.
- **The installer was built but not run here** (it would install on this machine); `--install-check`,
  which CI passes, installs it silently into a temporary folder and starts that.
- The icon: Bernardo chose B, the piston and crank (section 9).

## 11. Findings and decisions

- **MessagePortMain can't transfer an ArrayBuffer** (its `postMessage` takes ports only): a
  snapshot is cloned once. Measured above: about a millisecond at 64 KiB.
- **A control default that must be set:** `hold` 1 in the core means a dyno-held crank; the app
  builds `hold` 0.
- **The sandboxed window gets its port by `window.postMessage`** from the preload (ports can't
  cross the context bridge); the page takes it only from itself.
- **The decoder is generated** (`tools/gen_snapshot_ts.py`) and checked against the C's own example
  bytes; a bug it found in the tests: `instanceof ArrayBuffer` fails across realms, so it uses
  `ArrayBuffer.isView`.
- **Folder names:** `run_tests.py`'s copy skips anything called `build-*` and `build`, so the icon
  folder is `branding/` and the bundling script `bundle-node.mjs`.
- A killed engine on Windows exits with code 1 (the log says so); the first "starting" status has no
  pid, "running" has it.
- The theme choice isn't remembered (settings come later); the fake add-on's rpm is a first-order
  lag, not an engine.
- **Python suite on this machine:** `test_exhaust_geometry` needs `make` on PATH (w64devkit); it
  isn't on this shell's, so that one test errors here, unrelated to this stage.
