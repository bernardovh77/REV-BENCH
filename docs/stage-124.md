# Stage 124 — The application's foundation

Specification: [docs/roadmap/07-app.md](roadmap/07-app.md#stage-124), design:
[docs/app-design.md](app-design.md) sections 2–5, 9–13 and 15.

**Status: phase 1 done (the app shell, against a fake add-on); phase 2 (the real add-on, the
Electron end-to-end test, the measurements, the installer, CI) is still to do.** The add-on
(`app/native/`) is builder A's part of this stage and has its own record.

The stage ran in two parts so that two builders could work at once: builder A the Node-API
add-on, builder B the rest of `app/`, each against a fixed contract
([`app/src/shared/addon.ts`](../app/src/shared/addon.ts) for the add-on,
[`app/src/shared/protocol.ts`](../app/src/shared/protocol.ts) for the window and the engine
process). Neither contract was changed.

### Two builds, and why

- **The window** is built by Vite (`vite build`, root `src/ui`, output `dist/ui`): Svelte,
  the CSS, Inter from `@fontsource/inter` as files (no `data:` URIs, no inline script), and the
  policy as a `<meta>` made from `src/shared/csp.ts`.
- **The three Node-side programs** (main, preload, engine) and the fake add-on are built by
  `scripts/bundle-node.mjs`, which calls Vite's library mode once for each, to one CommonJS file:
  `dist/main/main.cjs`, `dist/preload/preload.cjs`, `dist/engine/engine.cjs`,
  `dist/engine/fake-addon.cjs`. Why not `tsc`: the same TypeScript and the same resolver as the
  window's build (`.ts` imports without `.js` suffixes), one pinned tool, and the sandboxed
  preload has to be a single file anyway. Types are checked apart (`npm run typecheck`).
  `electron` and Node's modules stay external. The fake add-on has its own file so a package can
  leave it out: the engine requires it only when `RB_FAKE_ADDON=1`.
- The folder name `bundle-node.mjs` (not `build-node.mjs`) is deliberate: `tools/run_tests.py`'s
  copy skips anything called `build-*`.

### How the engine process finds its add-on

`src/main/config.ts` reads the environment in the main process and tells the engine process in
its first message (`init`): `RB_FAKE_ADDON=1` means the fake, otherwise `native`.
`src/engine/addon-loader.ts` then looks for `rb_native.node` in `$RB_NATIVE_PATH`, then
`<resources>/rb_native.node` (a package), then `app/native/build/Release/rb_native.node` (cmake-js's
default output). **It never falls back to the fake**: a missing add-on is a `fatal` message, the
process exits, and the window says why (a planted bug checks it). Other variables, for tests and
developers: `RB_BACKEND=null` (no sound device), `RB_SAMPLE_RATE`, `RB_DEVICE`, `RB_USER_DATA`
(the user-data folder).

To see the shell today: `cd app; npm run build; RB_FAKE_ADDON=1 RB_BACKEND=null npx electron .`
(the first `electron` run downloads its binary: Electron 45 no longer does it in `npm ci`;
`npx install-electron` does it ahead).

### The channel

- The main process makes a `MessageChannelMain` for every request of the window and every
  restart of the engine, gives one end to the engine process (`connect`) and the other to the
  window (`webContents.postMessage`). The preload receives it and posts it to the page with
  `window.postMessage(msg, "*", ports)` (a port can't cross the context bridge as an argument);
  the page takes it only from itself and only with the right channel name.
- The window asks (`requestEnginePort`), so there's no race with the page's load; a reloaded
  window just asks again and the engine closes the old port.
- `src/engine/control.ts` is the protocol: `set-param` by name, `load-preset` as prepare, a
  polled wait and a swap (the reply is the swap's ack), `select-device`, snapshot and statistics
  requests. A reply always carries the window's own id. A rebuild that fails leaves the running
  engine alone and says why; only one at a time (`BUSY`); one that never finishes is given up
  after 30 s. Malformed messages are logged and ignored; nothing the window sends can throw in
  the engine.
- The window never waits: `EngineStore` asks for a snapshot every animation frame (statistics
  every 60), keeps the newest it decodes, and counts those the decoder refuses.

### Crash handling

`src/main/supervisor.ts` (no Electron inside, so it is tested with fakes): the engine is
restarted after 0.2, 0.5, 1, 2 and then 4 s; more than 5 deaths in 60 s is `failed`, which the
window shows with a button that asks for a fresh start; a saved build that keeps the engine from
starting (2 starts in a row that never got ready) is dropped for the default build; a crash
after the engine was ready is not counted as a failed start. The build the engine reports after
each rebuild is autosaved (`userData/session/build.json`, written atomically) and is what a
restart (and the next launch) uses. The window is told every step (`starting`, `running`,
`restarting` with why, `failed`) and gets a new port after each restart. Everything is logged to
`userData/logs/rev-bench.log` (kept to 1 MB, then `.1`), including the engine's stdout and
stderr.

### Security

`src/main/window.ts` and the tests in `tests/security.test.ts` (Electron's checklist, as far as
it applies to a window that only loads its own file):

1. sandbox on, context isolation on, Node integration off (also in workers and sub-frames);
2. web security on, no insecure content, no experimental features, no `<webview>`;
3. a strict policy (`default-src 'none'`, scripts, styles, images and fonts from `'self'`, no
   network, no frames, no forms, no base URI), checked in the built `index.html` too, together
   with "no inline script, no `style=`, no remote URL";
4. navigation, redirects and new windows refused;
5. every permission refused;
6. IPC trusted only from the app's own page;
7. nothing loaded from the network.

Also a source scan for `nodeIntegration: true`, `sandbox: false`, `eval`, `{@html}`,
`innerHTML =` and the like, and a test that the built preload is one file that needs nothing but
`electron` (all a sandbox allows). A real Electron run confirmed the window sees no `require` or
`process`, and that the policy blocks nothing the interface needs (no console violations).
Not yet done, for the packaged app (phase 2): Electron's fuses (`runAsNode` off and the rest;
Playwright's Electron driver needs the inspect-argument fuse in the build it drives).

### The snapshot decoder is generated

`tools/gen_snapshot_ts.py` reads `tools/snapshot_v2.py`'s tables (the header's offsets, the
instruments' and the cylinder fields' names, which stage 121 checks against the C) and writes
`app/src/shared/snapshot-v2.generated.ts`: a decoder that applies the contract's rules
(`parse`'s, one for one) and an encoder (used by the fake add-on and the tests, so nothing in the
app writes an offset by hand). It also writes `app/tests/golden/snapshot-v2-i4-idle.json`, what
`snapshot_v2.py` reads from `contracts/examples/snapshot-v2-i4-idle.bin`.
- `tools/test_gen_snapshot_ts.py` (Python suite): the committed files are what the generator
  makes today; a moved header field or a new instrument changes the generated text.
- `app/tests/snapshot.test.ts` (Vitest): the decoder reads every value of the C's example as
  Python does, the encoder writes the C's bytes back byte for byte, and every rule of the
  contract is refused when broken.
- The names stay the contract's own (snake_case). `Snapshot` replaces the header's count of
  instruments with the instruments by name, as `parse` does. 64-bit counters are numbers (a value
  past 2^53 is refused, not rounded); `build_id`, a hash, is a `bigint`.
- A bug found by the integration tests: `instanceof ArrayBuffer` fails for bytes that came
  through a MessagePort from another realm; the decoder uses `ArrayBuffer.isView`.

### The design system

`src/ui/design/tokens.css`: colour tokens in a dark theme (the default) and a light one, Inter
first in the font stack (`@fontsource/inter`, latin 400/500/600), a type scale, a spacing
scale, shapes, the sizes of the window's parts and one timing. Plain and provisional; when the
look is chosen, tokens.css and the base components change, not the panels (app-design §15). Base
components: Button (toggle, variants), Select, Readout (a number with its unit), Panel, Slider,
Notice. The layout (`AppLayout.svelte`) has the four regions; the editor, the centre and the
charts are empty (the centre shows the engine's messages when there is no engine). The top bar
has the engine's state, the preset (`load-preset`), ignition, starter (held), throttle, the
rpm and a theme switch (not remembered yet: settings come with their own stage).

`src/ui/design/lint.ts` is the rule as code: outside tokens.css, no colour (hex, colour
functions, names in colour properties, colour strings in scripts), no `font-family`, no
`font-size`/`font-weight`/`line-height`/`letter-spacing` that isn't a `var()`, no length with a
unit other than 0, no `style=` attribute, no `var(--x)` that tokens.css doesn't define.
`tests/design-tokens.test.ts` runs it over every `.svelte` and `.css` file of `src/ui` (the
panels, the layout, App and the base components alike), checks the two themes define the same
colours, that panels are built from the base components and not from raw `<button>`s, and
tests the linter on samples.

## Findings and decisions

- **Electron's `MessagePortMain` can't transfer an `ArrayBuffer`** (its `postMessage` takes only
  ports to transfer, `electron.d.ts`). The control loop passes the transfer list and the
  adapter for Electron's port drops it, so a snapshot is cloned once on its way to the window
  (464 bytes for a four, 624 for a V8: 60 a second is about 40 KB/s). Phase 2 measures it
  against runtime-v1's budget.
- A killed engine on Windows exits with code 1, not "killed"; the log says
  `the engine process exited (code 1)`.
- The engine's pid is known once it has started, so the first "starting" status and its log line
  have none; "running" has it.
- The theme choice is not remembered (settings come later); the window's background is the dark
  theme's, checked by a test.
- The fake add-on has a trivial first-order rpm so the instruments move. It is not an engine
  model and makes no sound.
- Electron 45's `npm ci` does not download the Electron binary (the first run does, or
  `npx install-electron`): CI needs that step (phase 2).
- The Playwright pin: `@playwright/test` is in the dependencies for phase 2 (its `_electron`
  launched the real app in a trial run: the window, the presets, a rev through the fake, a
  preset change, the killed engine's restart with the autosaved preset, the log file).
